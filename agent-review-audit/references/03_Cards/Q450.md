# Q450: CUDA Graph 与 Tensor Parallelism (TP) 融合通信挂死定位：在大模型分布式场景中开启 CUDA Graph 与 TP 出现卡死（Hang），为何关闭 Graph 或降 TP 仅是定位线索而非根因？如何通过最小变量矩阵与 Trace 工具排查？通信状态标记（flag）内存位置、内存模型与同步协议如何设计？修复验证方案应包含哪些维度？

> [!QUESTION] 问题描述
> CUDA Graph 与 TP 融合通信卡死定位：在大模型训练/推理开启 CUDA Graph 且 TP > 1 时出现进程死锁/卡死（Hang），为什么关闭 Graph 或将 TP 降为 1 现象消失只是“定位线索”而非“根因结论”？如何通过变量矩阵与 Profiler/Trace 工具逐步排查至融合通信算子？通信状态标记（flag）存放在何处、为何选用浮点类型、其内存一致性与同步协议在原实现中如何设计？修复后如何通过最小复现用例与模型级端到端回归进行验证？

> [!SUCCESS] 审查重点与证据要求
> - **必答点与核心考点**:
>   1. **定位线索与待验假设区别**: 关 Graph 或设 TP=1 消除卡死属于剥离变量的排查手段，不能直接草率得出“CUDA Graph 与 TP 存在先验不兼容”的结论（NCCL 官方已规范支持 CUDA Graph capture）。TP=1 规避了跨卡通信同步，关 Graph 则改变了流捕获与主机端调度的交互方式，两者均可能掩盖底层的未定义同步行为或并发竞争。
>   2. **排查收敛与 Trace 分析**: 构建 (Graph 开关, TP 规模, 输入 Shape, 数据类型) 变量矩阵；使用 Nsight Systems 或 PyTorch Profiler 捕获多 rank 时间轴上的 Stream 依赖、Kernel 启动顺序与 NCCL 集合通信调用，排查是否存在跨 rank 通信发起顺序不一致、Stream 事件未被图捕获记录或通信缓冲区非法重用等待验证假设。
>   3. **通信状态标记（Flag）与内存模型考察（向候选人澄清其实际选型）**:
>      - 考察 Flag 的物理存放位置（Device Global Memory, Pinned Host Memory, 或 Unified Memory）与多 rank 访问生命周期；
>      - 澄清硬件原子性与协议逻辑：CUDA 虽支持部分浮点 atomic 操作（如单双精度 `atomicAdd`），但普通浮点读写（load/store）绝不会因数据类型天然赋予跨设备/跨流的内存顺序、可见性或同步语义；
>      - 要求候选人结合真实工程说明：原协议是否配置了内存屏障（如 `__threadfence_system()`）、acquire-release 语义、volatile 限定词或专用同步原语；为何原设计选择浮点（是否出于 Tensor 缓冲区统一复用考量），以及原判断逻辑在何种并发时序下出现死锁。
>   4. **复现与模型级回归**: 设计不依赖大模型权重的独立双卡/多卡最小通信复现脚本；采用符合规范的 Stream Event 同步与官方 NCCL Graph 模式修复；在模型级流水线全面回归 Graph on/off、TP=1 与多 rank 下的数值一致性、运行稳定性与时延。
> - **追问方向**:
>   1. CUDA Graph 仅捕获 GPU Stream 上的工作与显式依赖，并不捕获脱离 Stream 的任意 CPU 端轮询逻辑。如果原同步协议依赖 CPU 主机轮询 Device 标志位，捕获进 Graph 后会引发何种行为？
>   2. 修复后的通信算子如何通过长时多轮并发测试（Stress Test）证明不会概率性引入新的跨 rank 死锁？
> - **易错边界与认知陷阱**:
>   - 严禁断言“CUDA Graph 先验与 TP 不兼容”；
>   - 严禁笼统断言“浮点完全不支持原子操作”（CUDA 支持部分浮点原子操作），但必须指出普通浮点读写不等于自动具备同步协议正确性与内存可见性；
>   - 原面经未提供具体源码时，应将 flag 放置与原同步机制作为开放性工程考察，要求候选人说明其真实设计，不虚构唯一的所谓“原 Bug 代码”。
