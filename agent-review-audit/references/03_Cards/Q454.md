# Q454: 国产 AI 加速卡算子 Benchmark 与多基线对齐评测方法论：在国产 GPU / AI 加速卡上对自研或适配算子进行性能评测时，如何设计严谨的 Benchmark 测试矩阵（涵盖不同 Shape、Batch Size、Sequence Length 与 Dtype）？为了消除评测偏差，Warmup 次数、计时方式（如硬件 Event 同步 vs CPU 计时）、Stream 同步与 CUDA Graph/执行图配置应如何标准化？如何与芯片厂商高性能库、旧有开源实现及自写 Kernel 进行同语义、公平基线（Fair Baseline）的对比？

> [!QUESTION] 问题描述
> 国产 AI 加速卡算子 Benchmark 与多基线对齐评测方法论：在国产 GPU / AI 加速卡上对自研或适配算子进行性能评测时，如何设计严谨的 Benchmark 测试矩阵（涵盖不同 Shape、Batch Size、Sequence Length 与 Dtype）？为了消除评测偏差，Warmup 次数、计时方式（如硬件 Event 同步 vs CPU 计时）、Stream 同步与 CUDA Graph/执行图配置应如何标准化？如何与芯片厂商高性能库、旧有开源实现及自写 Kernel 进行同语义、公平基线（Fair Baseline）的对比？

> [!SUCCESS] 审查重点与证据要求
> - **必答点与核心考点**:
>   1. **全维度测试矩阵**: 涵盖 Prefill（长输入小 Batch）与 Decode（短输入大 Batch）典型负载，覆盖 FP16、BF16 及量化格式；防止仅针对单一“黄金 Shape”调优导致在实际端到端场景中性能劣化。
>   2. **消除评测偏差的标准化流程**:
>      - **Warmup 预热**: 丢弃前 10~20 次运行，规避 JIT 编译、驱动初始化及冷启动显存分配开销；
>      - **硬件级计时**: 严禁在主线程使用纯 CPU `time.time()`；必须使用加速卡底层硬件事件（如 `cudaEventRecord` / 厂商等价 API）并在计时区间显式同步目标 Stream；
>      - **Cache 管理**: 根据测试目标（算子真实吞吐 vs 理想驻留性能）规范是否在迭代间执行 L2 Cache Flush。
>   3. **公平基线（Fair Baseline）同语义对比**:
>      - 明确对比三方基线：自写 Kernel、芯片厂商闭源/开源官方数学库、上一代遗留实现或主流开源标准库；
>      - 严格校验各基线在数学语义、累加器精度（如 FP32 Accumulator）及内存排布上的绝对等价性。
>   4. **瓶颈量化与迁移边界**: 结合 Roofline 模型分析当前算子达到理论显存带宽与算力利用率（MFU）的百分比，评估国产硬件编译器与指令集特性的迁移差异。
> - **追问方向**:
>   1. 国产加速卡在 Warp/Wavefront 宽度（如 32 vs 64）或内存对齐要求上若与 NVIDIA 架构不同，现有 Kernel 会产生哪些性能陷阱？
>   2. 当出现自写 Kernel 延迟降低但显存峰值翻倍时，如何从端到端部署视角权衡？
> - **易错边界与认知陷阱**:
>   - 严禁给出含糊且不可复现的“测试差不多”论述，必须详细说明计时原语与消除误差的具体规范。
>   - 严禁随意编造未经真实物理卡实测的具体厂商型号跑分数据。

>   - MLPerf Inference & Training Benchmarking Rules
