    来源：https://github.com/SuperGODOG/skillforge ｜ 文件 43 个 ｜ 语言 py×29、md×5、json×5、docx×1、toml×1

    技术栈

    Pydantic、HuggingFace Transformers

    画像（subagent 润色版）

    SkillForge 项目画像（面试向）

    定位：Agent Skill 自进化元 Agent 系统——"生产 Skill 的元 Agent 工厂"。4 周独立完成，4907 行 Python（1600 核心 + 3300 tests/scripts），pytest 74/74，CLI 一键复现全部数字。

    ① 技术栈与架构概览

    • 基座：Python 3.10+，扩展 hello-agents 1.0.0（继承 Tool / ToolRegistry / SimpleAgent，pyproject.toml）；Pydantic 2 定义 SKILL.md schema（models.py）
    • 模型：bge-small-zh-v1.5（本地 CPU embedding，sentence-transformers + modelscope）+ DeepSeek API（主 LLM + Judge 双角色）
    • 存储：SQLite（发布状态唯一事实源）+ Git（Skill 内容版本）+ JSONL（路由/评估审计），三处异构
    • 五大组件：SkillRegistry（use_skill 渐进式披露）→ IntentRouter（三层级联路由）→ SkillEvaluator（八维评估 + 棘轮）→ SkillEvolver（元 Agent 六步闭环）→ ReleaseStateMachine（SQLite 发布状态机）
    • 数字：路由 R@1=98% / R@3=100%（50 条硬负例调优，62%→98%）；21 条保底盲评（robust 19% ✓ / read 24% ✓ / task 62% ✗）；1 次真实元 Agent 迭代 L2 patch +4.90 分

    ② 30 秒自我介绍底稿

    我做了一个叫 SkillForge 的 Agent Skill 自进化元 Agent 系统。大多数 Agent 项目聚焦"用 Skill 干活"，我做的是让 Skill 本身可评测、可版本管理、可自动改进的闭环。三点核心：第一，渐进式披露——Skill 只以元数据索引暴露给 Agent，Agent 主动调 use_skill(name, reason) 才加载完整 Body，每次加载强制 reason 归因并写审计日志（registry.py）；第二，三层级联路由——规则层只做排序信号不独占决策，bge 向量层用结构化检索卡片，LLM 兜底，50 条硬负例把 R@1 从 62% 调到 98%（cascade.py）；第三，八维评估 + 棘轮 + 元 Agent 半自动闭环——Judge 用 A/tied/B 配对比较而不是绝对打分，元 Agent 生成 patch 按 L1/L2/L3 分级发布，L1 自动、L2/L3 只出建议（evolver.py）。系统 4907 行、74 个测试全绿、单命令复现。

    钩子清单（每个都能引向深挖）： - [H1 术语钩子] 渐进式披露 + use_skill(name, reason) 归因 → 追问：为什么不让框架自动注入 Skill？token 成本怎么算？归因链怎么回放？（代码：registry.py::use_skill 写 router.jsonl，build_index 只注入元数据两层披露） - [H2 对比钩子] Judge 配对比较 vs 绝对打分 → 追问：LLM-as-a-Judge 怎么防分数漂移？efficiency 维度为什么用客观 token 比不打分？task 维度 62% 盲评分歧这个坑怎么发现的？（代码：judge.py::PairwiseJudge，evaluator/__init__.py::_efficiency_score） - [H3 架构钩子] 三层路由：规则不独占 + Not For 检索卡片 → 追问：为什么早期"规则独占"会让 17/18 硬负例误命中？[Not For] 段如何在向量空间推远负例？阈值 0.75/0.10/0.35 怎么定的？（代码：cascade.py 阈值常量，embed.py::encode_card，rule.py 命中即等分） - [H4 架构钩子] 元 Agent 分级发布 L1/L2/L3 → 追问：AI 改 AI 的信任边界？为什么 L2 patch +4.90 分也只出建议？30% 成功率为什么是"坦诚"的？（代码：evolver.py::_publish_patch 分级逻辑，__log/2026-07-27-phase4-evolve/ 实录） - [H5 架构钩子] SQLite 唯一发布事实源 + 原子切换 → 追问：Git、SQLite、JSONL 三处存储一致性？release_id UUID 幂等怎么做？Watchdog 为什么清 PREPARING 不回滚 Git？（代码：state_machine.py 四步协议 + watchdog_sweep）

    ③ 框架给的 vs 我设计的

    层 框架/基础件给的 我设计的
    Agent 抽象 hello-agents：Tool/ToolRegistry/SimpleAgent/HelloAgentsLLM SkillRegistry 继承 ToolRegistry：SKILL.md frontmatter 解析、build_index 元数据索引、use_skill 渐进式披露 + SQLite→Git 读 Body 三级降级（git/disk_fallback/disk_no_release）
    路由 无（框架不提供） IntentRouter 三层级联：规则只记账不独占（命中即等分 100，防刷词）+ bge 结构化检索卡片（[Capability][Use When][Examples][Not For]）+ LLM 兜底可拒绝（返回 None）；阈值按硬负例评测集校准
    评估 无 八维评估器：结构 40 分静态检查（不阻断）+ 效果 60 分（Judge 配对三维 + 效率客观 token 比）+ P0 门槛；棘轮硬 5 条 DECLINED + 软 10% REVIEW（含上升，防"表面漂亮"）
    自进化 SimpleAgent 基类 SkillEvolver 六步闭环（收集失败→LLM 根因四标签→生成候选→沙箱验证→分级发布→归档），L1 自动 / L2 L3 只建议，失败 patch 沉淀 runs/failures/ 负样本
    发布协议 SQLite/Git/JSONL 为底层设施 ReleaseStateMachine 四步固定顺序 + BEGIN 事务原子切换 + UUID 幂等 + Watchdog 24h 清理孤儿

    ④ 最可能的面试追问点（对应题库概念）

    1. LLM-as-a-Judge 可靠性（评测体系与 Benchmark）→ 配对比较对抗漂移、Judge 调用失败返回 tied 兜底、judge_llm 可独立换模型降自评偏见；21 条盲评校准暴露 task 维度 62% 分歧 = Judge 幻觉盲区，已知缺陷 + 明确修复路径（Judge prompt 加"未验证数据=幻觉"红线）
    2. 路由检索质量与硬负例（路由机制 / RAG 检索）→ 50 条手工硬负例评测集、Not For 段主动推远、hit_layer 分层可归因；阈值来自调优实验（62%→98% 三步，见 __log/2026-07-26-router-hardnegative-fix/），不是拍脑袋
    3. 上下文管理与成本（上下文管理与压缩）→ 渐进式披露只两层：元数据索引常驻 system prompt，完整 Body 仅 use_skill 时占 token；效率分用 skill/baseline token 比（ratio=1→10 分）量化"Skill 到底省不省"
    4. 评测数据防过拟合（Badcase 闭环与数据飞轮）→ dev 32 条（元 Agent 可见）/ hidden 8 条（防过拟合）/ p0 10 条（core 门槛）分离；元 Agent 失败样本归档成负样本库，形成数据飞轮
    5. 多存储一致性 / 幂等（存储选型与状态持久化）→ SQLite 单事务原子切换 current_release_id；release_id UUID 幂等重放；任一步失败停在 PREPARING，旧版本继续生效；Watchdog 清孤儿而非回滚 Git（保留审计价值）
