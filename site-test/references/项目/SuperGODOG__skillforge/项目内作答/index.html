    项目内作答 · 架构/框架/Prompt/技能主题

    范围：match.json candidates 中 L6 / L74 / L80 / L93 / L9 / L150 / L34 / L137 / L49 共 9 题。 证据路径基准：src/skillforge/...、scripts/...、skills/... 均相对仓库根目录；README.md、ARCHITECTURE.md 在仓库根目录；__log/ 为事件复盘证据。

    L6 请介绍一下常见的 Agent 工作流范式（如 ReAct、Plan-and-Execute 等）的区别与适用场景。

    一句话回答：ReAct 是"思考-行动-观察"逐轮决策，Plan-and-Execute 是先计划后执行；SkillForge 兼用两者——Agent 层 use_skill 显式加载是 ReAct，元 Agent 六步 pipeline 是 Plan-and-Execute。

    展开细节： 一、ReAct 落地：系统基于 hello-agents 的 ReActAgent（README 架构简图），Skill 加载完全由 Agent 决策——注册 use_skill(name, reason) 特殊工具由 Agent 在循环中显式调用（src/skillforge/registry.py:123），reason 必填形成归因链，"归因 100% 可回放，ReAct 可解释性无断点"（README 五大设计决策 1）；完整 Body 只在调用时注入、不拦截 prompt（ADR-01，ARCHITECTURE.md §8）。 二、Plan-and-Execute 落地：SkillEvolver 元 Agent 的六步 pipeline 是典型的先规划后执行——evolve_full 固定顺序 baseline → collect → root_cause → generate → validate → publish/archive（src/skillforge/evolver.py:111），每步产出类型固定、可独立验证，与 ReAct 的自由探索形成对照。 三、适用场景取舍：路由层"三层级联"是决策分层的工程化——规则/embed/LLM 按置信度逐层 fallback（src/skillforge/router/cascade.py:70 route），中间地带交 LLM 二选一（src/skillforge/router/llm.py:36 choose）；发布协议则用状态机四步固定顺序 begin_release→write_commit→append_evaluation→commit_release 保证原子性（src/skillforge/state_machine.py:49-140）。结论：可确定的流程用 Workflow 锁死，开放决策交 Agent，混合是工程常态。

    L74 在AI应用架构中，旨在统一大模型与外部数据源或工具集成接口的连接协议（如Model Context Protocol / MCP），其本质和核心设计思想是什么？

    一句话回答：MCP 本质是"统一工具接入协议"——一次接入、处处复用、按需取数；SkillForge 用 SKILL.md 的 dependencies 声明 + 两段式披露实现了同一思想的轻量版，MCP 协议接入列为 Roadmap。

    展开细节： 一、项目中的工具抽象：SKILL.md 通过 dependencies: [amap_weather_api] 显式声明外部工具依赖（skills/weather_query/SKILL.md:14），结构分把"依赖可用性"作为独立检查项（deps 满分 5，src/skillforge/evaluator/structure.py:44-46），注释明确 Phase 4+ 可扩展为 subprocess.which / MCP ping——"工具即声明、按需解析"，与 MCP 把工具资源化的思想同源。 二、按需取数的上下文管理：渐进式披露只两层——元数据索引（build_index 输出 name/description/use_when/not_for，src/skillforge/registry.py:71-89）常驻 prompt，完整 Body 仅在 Agent 调用 use_skill 时才注入（registry.py:123）；ARCHITECTURE.md §4.1 场景 A 展示了 Agent 按 Body 的 Instructions 调用 amap_mcp_server 的完整链路。这正是 MCP"只有工具描述常驻上下文、数据按需返回"的设计动机。 三、诚实说明与下一步：本项目当前未实现 MCP 协议——README Roadmap 第 3 项明确"接入 MCP 协议——生态化被 Claude Desktop / Cursor 消费"；现有 Skill 依赖是协议无关的字符串声明。若落地，接入点清晰：把 3 个种子 skill 的 dependencies 映射为 MCP server（JSON-RPC over stdio），use_skill 加载 Body 后由 MCP 客户端统一解析工具调用。

    L80 在大模型应用落地中，确定性工作流（Workflow）与自主智能体（Agent）在业务场景选择、决策机制及容错成本上有何本质区别？如何理解自主智能体（Agent）与工作流（Workflow）的区别、联系及适用场景？

    一句话回答：Workflow 是"代码决定流程"，Agent 是"模型决定流程"；SkillForge 用三层级联路由把确定性（规则/阈值）与自主性（LLM）按置信度分层，用硬负例评测集校准边界。

    展开细节： 一、决策机制差异：路由层规则只做"记账"——keyword 命中即等分 100.0、不加权（src/skillforge/router/rule.py:20-29），不独占决策；embed 层 top1 ≥ HIGH_CONF=0.75 且 margin ≥ 0.10 才独占（src/skillforge/router/cascade.py:32-34,99-100）；中间地带交 LLM（llm.py:36）。这就是"确定性的归代码、不确定的交模型"的显式分层。 二、容错成本：Agent 决策不可穷举，因此设计"保守拒绝"护栏——top1 < LOW_CONF=0.35 直接拒绝不进 LLM（cascade.py:103-105）；LLM 调用失败返回 None 拒绝路由（src/skillforge/router/llm.py:79-81）；bge 模型缺失降级到"规则唯一命中才决策"（cascade.py:81-87）；Judge 失败 tied 兜底（src/skillforge/evaluator/judge.py:73-75）。Workflow 的容错在开发期写全分支，Agent 的容错在运行期兜底。 三、场景选择实证：首版"规则独占命中直接决策"（纯 Workflow 式）在 50 条硬负例上总 R@1 仅 62%，18 条硬负例错 17 条（"帮我写一个正则匹配邮箱"命中"正则"→误选 explain_regex）；改为规则不独占 + LLM 兜底 + prompt 给 not_for 后 R@1=98%、R@3=100%（__log/2026-07-26-router-hardnegative-fix/README.md）。结论：字面匹配用规则、意图匹配交语义层——"不写死百分比，靠置信度门槛"（README 设计决策 2）。

    L93 在复杂的、多步骤的任务场景中，Agent应如何进行任务拆解、步骤规划和动态决策？你是否实践过ReAct、ToT（Tree of Thoughts）等框架或相关思路？

    一句话回答：项目用"固定 pipeline 拆解 + LLM 根因分析驱动候选生成 + 多候选沙箱验证"实现拆解与规划；ReAct 是 Agent 层基座，ToT 未用，但多候选验证实现了等价于 beam-search 的思路。

    展开细节： 一、任务拆解：元 Agent 六步 pipeline 把"改进一个 Skill"拆成可独立验证的步骤——evolve_full 中 1-baseline 评估拿基线 → 2-_collect_failures 从 case_verdicts 拉 B_better 失败样本（src/skillforge/evolver.py:231）→ 3-_analyze_root_cause 输出四类根因标签 trigger_inaccurate/prompt_vague/deps_broken/boundary_missing 及概率（evolver.py:284）→ 4-_generate_patches 生成 N 个完整新 SKILL.md（evolver.py:351）。 二、步骤规划与动态决策：规划约束写进 prompt——_PATCH_GEN_PROMPT 强制 L1/L2/L3 分级、version bump、至少 2 个 L1（evolver.py:319-350）；决策由数据驱动（根因概率排序决定生成重点）；验证是动态闭环——_validate_patch 把 patch 落到临时 <name>__candidate 目录、独立 registry 跑评估、棘轮判定、finally 清理（evolver.py:398-448）。 三、ReAct/ToT 对照：ReAct 体现在 Agent 层 use_skill 显式 tool call（registry.py:123）与路由层逐层决策；ToT 未直接使用，但"一次生成 3 个候选 + 逐一沙箱验证 + 失败归档 runs/failures/"（evolver.py:516-558）在效果上等价于 beam-search 式多候选评估，成本远低于树搜索；真实迭代中 L2 patch +4.90 分被 REVIEW、2 个 L1 被 DECLINED 归档（__log/2026-07-27-phase4-evolve/README.md），证明多候选 + 门槛验证能拦住"表面变好"的改动。

    L9 多Agent系统（Multi-Agent System）的编排模式有哪些？在框架选型（如LangChain、LangGraph、AutoGen等）时有哪些核心考量因素？

    一句话回答：编排模式分管道、层级监督、群聊等；SkillForge 是"主 Agent + 元 Agent + 评估器"的分层半自动编排，选型考量是轻量扩展、SQLite 状态机保证原子发布、CLI 可演示。

    展开细节： 一、项目编排模式：不是多 Agent 对话协作，而是三层分工——hello-agents ReActAgent（主 Agent，消费 skill）、SkillEvolver 元 Agent（继承 SimpleAgent，src/skillforge/evolver.py:87-98，负责生成候选）、SkillEvaluator（以 Tool 形态注册，src/skillforge/evaluator/__init__.py:41-48，负责判定）；协作通过共享 SkillRegistry + SQLite + runs/ 文件完成，L1 自动发布 / L2/L3 只出建议（src/skillforge/evolver.py:450-488）即"人工在环的 supervisor"角色。 二、框架选型核心考量：选 hello-agents 而非 LangGraph/AutoGen 的理由——(1) 规模匹配：~900 行核心预算 + CLI 演示定位（ARCHITECTURE.md §1），单进程模型（ADR-10）不引入队列；(2) 发布正确性交给 SQLite 状态机：release_id UUID v4 幂等、PREPARING→PUBLISHED 原子切换、Watchdog 24h 清理孤儿（src/skillforge/state_machine.py:49-163），这是图编排 checkpoint 的轻量替代；(3) 可测性：tests/test_state_machine.py、test_evolver.py 覆盖幂等与回环。 三、对照与演进成本：LangGraph 强在显式图/回环/持久化，AutoGen 强在协商对话；本项目各角色边界清晰（registry 管加载、router 管选择、evaluator 管判定、evolver 管生成），无需协商式编排；若未来要支持"多 Skill 协作任务"，可在 Registry 之上加 supervisor Agent，现有 use_skill 工具接口零改动——扩展点已预留。

    L150 提示词注入（Prompt Injection）与大模型越狱（Jailbreak）的区别与联系是什么？如何优化Prompt的鲁棒性，并有效防范提示词注入与越狱等安全风险？

    一句话回答：注入攻击"应用的数据流"（恶意指令混入用户/工具内容），越狱攻击"模型的对齐边界"；防御核心是"指令-数据分层 + 结构化输出白名单 + 保守拒绝"，项目在路由与评估 prompt 中均有落地。

    展开细节： 一、区别与联系：二者都发生在 prompt 空间。路由层 prompt 是分层典型——_PROMPT_TEMPLATE 把系统指令（"你是严格的意图路由器" + 4 条判定规则）与数据（{query}、{candidates_block}）分离（src/skillforge/router/llm.py:14-29），规则 1 强制"命中 not_for 必须 NONE"、规则 4"宁可 NONE 也不硬选"（错选比拒绝代价更高）——这是对注入式误导的指令级防御。 二、输出侧鲁棒性：_parse 只做白名单提取——LLM 响应中仅认候选 skill_name 精确子串（最长优先）或 NONE，解释/引号/换行全被容错消化（llm.py:92-108），恶意输出无法进入执行路径；Judge 同样限定三选一 A_better/tied/B_better（src/skillforge/evaluator/judge.py:27-44,78-98）；robustness 维度定义显式包含"是否幻觉/编造未知信息"（judge.py:20-26）。 三、架构级缓解与局限：Agent 只能通过注册的 use_skill 工具加载 skill，trigger.keywords 只作路由信号不做自动展开（README 设计决策 2）——恶意查询无法借 keyword 自动注入 Body，这是渐进式披露对注入的结构性防御；weather skill Constraints 明令"API 返回错误：不生成虚构数据"（skills/weather_query/SKILL.md:34-36）。盲评发现 Judge 对编造天气数据幻觉识别弱（task 维 62% 分歧，__log/2026-07-27-phase3-blind-eval/README.md）并定位改进方向；诚实说明：项目未做输入侧注入检测器，完整防御还需输入清洗 + 工具最小权限 + 敏感操作确认。

    L34 在基于 Harness 的自动评估与执行框架下，如何通过 Prompt Engineering 或 RAG 策略降低 Human-in-the-loop（人工介入）的成本？

    一句话回答：把人工审核翻译成"自动评估 harness + 棘轮自动判定 + 元 Agent 自动改 prompt + 人工只审高风险 L2/L3"，并用盲评抽检校准 Judge 而非全量人工。

    展开细节： 一、Harness 自动化替代人工：四套评估集（baseline_dev 32 / baseline_hidden 8 / p0_cases 10 / router_negatives 50，README 项目结构）全自动执行——evaluate_skill 对每个 case 跑"无 Skill vs 有 Skill"两版输出交 PairwiseJudge 配对比较（src/skillforge/evaluator/__init__.py:81-178），胜=1/平=0.5/负=0 加权为 task 25 / robust 15 / readability 10 分（_dim_score:250）；效率维走客观 token 比不用 LLM 打分（_efficiency_score:262），规避主观偏见。 二、Prompt Engineering + 自动闭环：棘轮把"要不要人工看"自动化——硬门槛 5 条（总分/效果分退步、task/robust 降 ≥5%、P0 由过变败）自动 DECLINED，软门槛任一维度变化 ≥10%（含上升，防"表面漂亮"）触发 REVIEW（src/skillforge/evaluator/ratchet.py:23-25,44-116）；元 Agent 六步自动生成 patch 并沙箱验证（evolver.py:111），L1 自动发布、L2/L3 只出建议——人工介入从"逐 case 审核"降到"审 L2/L3 建议"（__log/2026-07-27-phase4-evolve/README.md 分级规则表）。 三、抽检与数据飞轮（RAG 侧）：盲评抽样替代全量人工——scripts/blind_eval_run.py 每 skill 取 7 条共 21 条，human proxy 填 golden verdicts，偏差报告定位 Judge 幻觉盲区（__log/2026-07-27-phase3-blind-eval/README.md）；失败/建议 patch 全量归档 runs/failures/ 与 runs/suggestions/（evolver.py:516-558），下一轮元 Agent 读取负样本避免重犯——badcase 回流 prompt 迭代，是 HITL 成本随轮次递减的根本机制。

    L137 在Agent或插件化系统中，系统的技能（Skills/Plugins）动态加载与初始化流程是如何设计的？

    一句话回答：初始化 = 目录扫描 + frontmatter 解析 + Pydantic 强校验注册；动态加载 = Agent 显式 use_skill(name, reason)，按 SQLite→Git→磁盘三档降级取 Body，每次调用写归因日志。

    展开细节： 一、初始化/注册流程：load_skills_from_dir 扫 skills/*/SKILL.md，_FRONTMATTER_RE 正则切 YAML frontmatter 与 Body（src/skillforge/registry.py:23），yaml.safe_load 后由 Pydantic SkillMeta 强校验（src/skillforge/models.py:21-30：name/version/description/use_when/not_for/dependencies/trigger/examples），name 冲突直接 ValueError 拒绝（registry.py:50-68）——"初始化即校验"，坏 skill 进不了系统。 二、两段式披露与动态加载：启动时仅 build_index 生成元数据索引（name+description+use_when+not_for，registry.py:71-89）注入 system prompt；Agent 决策后调 use_skill(name, reason) 才加载完整 Body——优先级：SQLite 查 current_release_id → Git read_file_at_commit 读发布版，失败降级磁盘 body 并标记 source（git / disk_fallback / disk_no_release）（registry.py:123-169）；未注册返回 [ERROR] 可读文本不抛异常，Agent 可降级继续（registry.py:139-143）。 三、运行时动态加载的更多场景：路由侧 bge 索引懒加载——_ensure_indexed 首次 route 才编码 skill 检索卡片并缓存向量（src/skillforge/router/cascade.py:64-68，embed.py:60-67）；元 Agent 沙箱验证动态挂载/卸载——_validate_patch 创建临时 <name>__candidate 目录、独立 registry 加载、finally 中 shutil.rmtree 清理（evolver.py:398-448）。三处动态加载（use_skill 读 Body / embed 建索引 / candidate 沙箱）共用同一套 SkillMeta 解析协议，加载逻辑统一。

    L49 当Prompt优化达到瓶颈后，后续的性能提升路径如何规划？是进行模型选型替换、调整超参数，还是转向SFT/DPO？

    一句话回答：瓶颈后不盲目 SFT——先走"评估驱动调参 + 模型配置化 + 数据飞轮"：用评测集校准阈值（62%→98%）、Judge 可换更强模型、元 Agent 自动迭代 prompt；SFT/DPO 等 badcase 数据集积累后再启动。

    展开细节： 一、先"评估驱动调参"而非换模型：项目最大 prompt 收益来自用 50 条硬负例评测集校准路由——HIGH_CONF 0.55→0.75、MARGIN 0.05→0.10、LLM prompt 候选块扩到 use_when+not_for 三步调优，R@1 从 62% 到 98%（src/skillforge/router/cascade.py:32-34 注释 + __log/2026-07-26-router-hardnegative-fix/README.md Step 3）；复盘"教训 3"明确：调阈值先看 top1 相似度分布，不是拍脑袋——这是超参数调整的正确姿势。 二、模型选型路径已配置化：LLM 全部经 .env 注入（LLM_API_KEY / LLM_MODEL_ID=deepseek-chat / LLM_BASE_URL，README Quick Start），cli.py 与 scripts/eval_router.py 启动时读取（src/skillforge/cli.py:157-175）；评估器支持 judge_llm 独立参数——"生产可换独立更强模型降自评偏见"（src/skillforge/evaluator/__init__.py:34-47），即换模型零代码改动；LLM 调用失败有保守拒绝兜底（llm.py:79-81）。 三、SFT/DPO 的前置条件与诚实路线：项目明确不做盲目微调——口径"元 Agent 是候选生成器不是最终决策者，成功率 ~30% 坦诚"（README 数字对账）；路径是数据飞轮先转：runs/failures/ + runs/suggestions/ + evaluations.jsonl 持续沉淀 badcase（evolver.py:516-558），README Roadmap #4"10 次真实迭代 + 统计报告"兑现 30% 数字，此后才谈得上用"输入-修正后 SKILL.md"对做 SFT 对齐 _PATCH_GEN_PROMPT 的分级规则、用"验证通过 vs 失败 patch"构造 DPO 偏好对。规模小的 Agent 系统，prompt + 阈值 + 评估闭环的 ROI 远高于微调。

    L17 在意图识别与前置拦截（Guards/Gatekeeping）环节，如何设计并引入上下文记忆机制（Memory Mechanism）？

    一句话回答：本项目把"记忆"拆为三层——索引注入的静态上下文、router.jsonl 事件记忆、评估失败样本经验记忆；护栏由 not_for + LOW_CONF 拒绝 + LLM 强制 NONE 构成。

    展开细节： 一、前置拦截即三层路由的拒绝语义：规则层只做记账、不独占决策（src/skillforge/router/cascade.py:75-76）；embed 层 top1 < LOW_CONF=0.35 直接拒绝、不进 LLM（cascade.py:102-104）；LLM 层 prompt 明写"命中 not_for 必须 NONE / 宁可 NONE 不硬选"（src/skillforge/router/llm.py:18-22）——错选比拒绝代价更高，这是 Guards 的核心口径。 二、静态上下文记忆：SkillRegistry.build_index() 只暴露 name/description/use_when/not_for（每 skill ~80 token）随 system prompt 注入，Agent 决策不必看完整 Body（src/skillforge/registry.py:71-88）；完整 Body 由 use_skill(name, reason) 显式加载并强制 reason 归因（registry.py:123-169）。 三、事件记忆与经验记忆：每次 use_skill 追加 router.jsonl（ts/name/reason/source/latency_ms/release_id，registry.py:181-195）可回放归因；更长期的经验记忆是评估闭环——EvalResult.case_verdicts/case_outputs 落 JSONL（src/skillforge/evaluator/init.py:119-150），元 Agent 用 _collect_failures 读取 B_better 失败样本驱动迭代（src/skillforge/evolver.py:231-252）。即：意图拦截不依赖记忆，记忆服务归因与迭代。

    L19 在 Agent 架构中，长短期记忆模块（Short/Long-term Memory）的具体实现方案与状态持久化策略是什么？

    一句话回答：三处异构存储实现分级记忆——SQLite 存发布状态（短期指针）、Git 存内容全历史（长期记忆）、JSONL 存评估/路由轨迹（审计记忆），以 release_id 幂等串联。

    展开细节： 一、短期记忆=当前版本指针：skills.current_release_id 指向 releases 表 PUBLISHED 行（src/skillforge/storage/db.py:12-18），use_skill 先查 SQLite 拿 release_id+commit_hash，再 git show 读 Body，失败降级磁盘（src/skillforge/registry.py:148-162）；SkillMeta.evaluation.last_score/last_release_id 记录上次评估（src/skillforge/models.py:18-21）。 二、长期记忆=Git 全历史：write_commit 把每次 patch 落 git commit 并回写 commit_hash（src/skillforge/state_machine.py:67-88；src/skillforge/storage/git_ops.py:25-46），read_file_at_commit 可回溯任意版本（git_ops.py:49-51）；releases 表保留每次发布尝试（含失败/ABANDONED）构成版本记忆（db.py:20-32）。 三、持久化协议与一致性：四步固定顺序 begin_release(PREPARING)→write_commit→append_evaluation→commit_release 原子切换（UPDATE ... WHERE status='PREPARING'，state_machine.py:110-139），release_id UUID v4 幂等重放；Watchdog 24h 把孤儿 PREPARING 标 ABANDONED（state_machine.py:142-159）；evaluations.jsonl 每次评估一行供审计（state_machine.py:91-107）。

    L21 记忆的写入与读取，是采用大模型自主决策（LLM-routed）还是基于规则路由（Rule-based Router）更合理？

    一句话回答：用"确定性优先、LLM 兜底"的混合路由：规则与阈值能定就不调 LLM，仅中间地带交 LLM 二选一，按 50 条硬负例评测集把 R@1 从 62% 调到 98%。

    展开细节： 一、确定性层优先：RuleLayer 命中即等分 100（不加权，防塞冗余 keyword 刷分，src/skillforge/router/rule.py:1-9）；embed 层 top1 ≥ HIGH_CONF=0.75 且 margin ≥ MARGIN=0.10 独占决策，< LOW_CONF=0.35 直接拒绝（src/skillforge/router/cascade.py:31-34,99-104）——约 0.01~50ms 出结果。 二、LLM 只兜中间地带：top1 落 0.35-0.75 才调 LLM 二选一（cascade.py:106-111），prompt 给全 use_when+not_for 并强制"命中 not_for 必须 NONE"（src/skillforge/router/llm.py:11-26）；LLM 调用失败返回 None 等价拒绝，不阻塞主链路（llm.py:76-80）。 三、依据是评测而非拍脑袋：首版规则独占决策致 18 条硬负例 17 条误 route（总 R@1=62%），改"规则只记账 + LLM 兜底 + not_for 进 prompt"三步调优到 98%（__log/2026-07-26-router-hardnegative-fix/README.md:30-57）；scripts/eval_router.py 按 targets R@1≥80%/R@3≥90% 出 Recall 报告（scripts/eval_router.py:29-71），tests/test_router.py 固化规则层语义（tests/test_router.py:25-46）。

    L16 针对类似 Claude Code / GitHub Copilot Workspace 的 AI Coding 工具，其底层的 Agentic Workflow 与系统架构是怎样的？

    一句话回答：SkillForge 正是 AI Coding 工具的技能基础设施层：ReAct Agent + 显式 use_skill 工具调用 + 三层路由 + 八维评估闭环 + SQLite 发布状态机，加载归因可回放。

    展开细节： 一、Agent 主导渐进式披露：拒绝加载器拦截 prompt，注册 use_skill(name, reason) 特殊工具由 ReAct Agent 显式调用，reason 强制归因（src/skillforge/registry.py:123-169）；加载是显式 action，router.jsonl 每条含 name/reason/source/latency，ReAct 可解释性无断点（README.md:291）。 二、技能分发：元数据索引 build_index() 注入 system prompt（每 skill ~80 token），多候选时 IntentRouter 三层级联（规则→bge-small→LLM 兜底）按置信度 fallback、不写死百分比（README.md:293；src/skillforge/router/cascade.py:70-115）。 三、工程闭环：SkillEvaluator 八维评估 + 棘轮门槛决定能否发布；ReleaseStateMachine 以 SQLite 为唯一事实源做 Git+SQLite+JSONL 跨存储原子发布（README.md:299；src/skillforge/state_machine.py:49-159）；SkillEvolver 元 Agent 六步迭代（收集失败→根因→候选→沙箱验证→分级发布→归档）构成自进化（src/skillforge/evolver.py:105-225）。整体时序见 ARCHITECTURE.md §4-A（ARCHITECTURE.md:187-220）。

    L27 在多轮对话（Multi-turn Dialogue）中，如何解决指代消解（Coreference Resolution）和上下文省略的问题？

    一句话回答：本项目以单轮为主，处理上下文省略靠两条：结构化抽取（多轮对话压成素材）与渐进式披露（索引层控制上下文占用），语义消解交给 LLM 层。

    展开细节： 一、诚实边界：评估器按 SimpleAgent 单轮实现，turns 恒为 1（src/skillforge/evaluator/metrics.py:3-7），项目不做多轮状态管理——把多轮问题转化为"上下文压缩 + 结构化抽取"。 二、上下文省略的工程解法：write_weekly_report 的 wr_d08 case 要求从多轮对话片段抽取周报要点（"A: 项目 A 上线了 B: 恭喜…"→结构化四段，evaluation_sets/baseline_dev.json:27），即用 Skill 把省略主题的多轮文本压缩为结构化素材；wq_d08（"北京和上海今天温差多少"）验证多实体消解（baseline_dev.json:16）。 三、控制上下文占用即治本：索引层只注入 ~80 token/skill 元数据，完整 Body 按需 use_skill 加载（src/skillforge/registry.py:71-88；INTERVIEW_PREP.md:21-23），避免多轮累积撑爆上下文；语义消解交给 LLM 路由层——候选带 use_when+not_for 判意图归属（src/skillforge/router/llm.py:15-22）。metrics.py:27-30 已预留按 assistant 消息数计 turns 的扩展点，接多轮时直接启用。

    L30 在Agent/RAG pipeline中，Query改写（Query Rewriting）模块最适合放在哪个阶段？

    一句话回答：改写应放在检索之前的路由/理解阶段；本项目无独立改写模块，用"结构化检索卡片 + LLM 语义判定"在路由层完成等价功能。

    展开细节： 一、位置结论：Query 改写必须发生在检索前——本项目把"理解"内嵌在 IntentRouter 第一跳：EmbedLayer 将 query 编码后与 skill 检索卡片比对（src/skillforge/router/embed.py:69-85），卡片本身是 [Capability][Use When][Examples][Not For] 四段结构化文本（embed.py:47-58），相当于把"文档侧改写"前置到索引构建时。 二、改写即双向：Not For 段让 write_weekly_report 的 not_for=["会议纪要","月报"] 在向量空间主动排斥"帮我写会议纪要"这类硬负例（embed.py:1-14）；LLM 兜底层把 query+use_when+not_for 一起判意图（src/skillforge/router/llm.py:15-22），对 wq_d07"去南京出差看穿衣建议"这类外延查询靠语义理解而非字面改写（evaluation_sets/baseline_dev.json:15）。 三、落地建议：若加显式改写模块，应插在路由之前、与规则层并列，且改写结果必须可归因——router.jsonl 已留 scores/hit_layer 字段（cascade.py:117-130），存储层 jsonl/git/db 三处可支撑改写日志审计（src/skillforge/storage/jsonl.py:11-14）。

    L57 在知识检索和问答场景中，什么情况下基于规则/意图识别的确定性链路比大模型生成链路更具优势？

    一句话回答：确定性链路在"意图可枚举、成本敏感、需要明确拒绝语义"时胜出；本项目把 0.01ms 的规则层作为第一跳，LLM 只兜中间地带。

    展开细节： 一、延迟与成本：规则层 keyword 子串命中 0.01ms 秒回，embed ~50ms，LLM ~500ms（ARCHITECTURE.md:255）；实测评测集约 40% query 进 LLM 层，单次期望成本约 0.0004 元（INTERVIEW_PREP.md:50-52）——明确领域词命中（"我要写周报"）用规则 3ms 出结果，比每次调 LLM 省 15 倍。 二、拒绝语义与可控性：LOW_CONF=0.35 直接拒绝、不值得跑 LLM（src/skillforge/router/cascade.py:102-104）；LLM 调用失败返回 None 等价拒绝（src/skillforge/router/llm.py:76-80）；"宁可 NONE 不硬选"保证硬负例（"帮我写正则匹配邮箱"）不被误 route，硬负例 R@1 从 5.56% 提到 100%（__log/2026-07-26-router-hardnegative-fix/README.md:11-13,60-65）。 三、可归因与可评测：hit_layer 字段记录决策发生在哪层，路由错误可归因（cascade.py:117-130）；确定性阈值由评测集校准而非拍脑袋（cascade.py:31-34）；评估侧同理——效率维度用客观 token 比、不用 LLM 打分（src/skillforge/evaluator/metrics.py:1-7）。结论：能穷举意图的入口用确定性链路，开放域语义才交 LLM。

    L55 混合检索（Hybrid Search）的必要性是什么？向量检索（Dense Retrieval）与关键词检索（Sparse Retrieval/BM25）各自的优势与互补场景是什么？

    一句话回答：本项目以"规则层 + bge 向量层级联"实证混合检索：keyword 保字面召回、向量保语义召回，歧义交 LLM，R@1 达 98%。

    展开细节： 一、Sparse 侧（关键词）优势：RuleLayer keyword 子串命中，快（0.01ms）、字面精确、不依赖模型（src/skillforge/router/rule.py:14-30）；"命中即等分"防止冗余 keyword 刷分（rule.py:1-9）。局限：无法处理同义改写，"这周做了 A B C 三件事"不含"周报"仍需语义层。 二、Dense 侧（向量）优势：bge-small-zh-v1.5 编码检索卡片，余弦相似度 top-K 召回语义近邻（src/skillforge/router/embed.py:60-85），能匹配"帮我起草这周的工作汇报"这类无字面命中 query（evaluation_sets/router_negatives.json:41）；结构化卡片 [Capability][Use When][Examples][Not For] 拉开字面相近意图不同的 skill（embed.py:1-14）。 三、融合方式与本项目边界：采用"级联判定"而非分数融合——规则只记账、embed 高置信独占、中间地带 LLM 兜底（src/skillforge/router/cascade.py:75-115），阈值按 50 条硬负例调优（cascade.py:31-34）；诚实边界：无 BM25 实现、无向量数据库/HNSW，3 个 skill 规模全量点积即可（embed.py:83），候选规模上万才需 FAISS/ES 类索引。

    L213 在 Agent 与大模型应用中，常用的存储数据库（如关系型、NoSQL、向量数据库）的选型标准是什么？

    一句话回答：按"数据形态×一致性需求"选型：SQLite 管发布状态（事务+唯一事实源）、Git 管内容版本、JSONL 管审计流，向量检索用内存点积不引外部库。

    展开细节： 一、关系型（SQLite）：发布状态机需要事务与约束——skills/releases 两表 + status 索引（src/skillforge/storage/db.py:12-36），commit_release 用 BEGIN + UPDATE ... WHERE status='PREPARING' 保证原子切换与幂等（src/skillforge/state_machine.py:110-139）；硬约束"无外部 DB 服务"下 SQLite 单文件零运维（ARCHITECTURE.md:15-19）。 二、内容与审计：SKILL.md 是文本资产，选 Git 做版本管理——commit_skill 幂等提交、read_file_at_commit 按 commit 回溯（src/skillforge/storage/git_ops.py:25-51）；评估/路由轨迹是只追加流，选 JSONL（append/read_all，src/skillforge/storage/jsonl.py:11-22），天然适配审计与 Phase 4 失败样本读取（src/skillforge/evolver.py:231-252）。 三、"不选向量库"也是选型：3 个 skill 规模下 embed 层归一化后全量点积（dot=cosine，src/skillforge/router/embed.py:66-83），无需 HNSW/FAISS。选型标准总结：关系型管"状态与事务"、内容型管"版本与 diff"、日志型管"追加与审计"、向量库只在候选规模大到线性扫描不可接受时引入。

    L43 在缺乏用户主动反馈（如点击、点赞点踩）的数据场景下，如何设计自动化的抽检与评估机制？

    一句话回答：用"LLM-as-judge 配对比较 + 定期人工盲评校准 + 棘轮硬门槛自动阻断 + 失败样本自动回流"四件套替代用户反馈，分歧 <30% 作为 Judge 可信度门槛。

    展开细节： 一、自动化评估主链路：无反馈就用"有 Skill vs 无 Skill"双版本跑 case，PairwiseJudge 按 task_completion/robustness/readability 三维出 A/tied/B 配对判定（src/skillforge/evaluator/judge.py:47-91），配对比较对抗分数漂移（judge.py:1-10）；棘轮 5 条硬门槛任一触发即自动 DECLINED、无需人看（src/skillforge/evaluator/ratchet.py:44-79）。 二、抽检与校准：scripts/blind_eval_run.py 每 skill 抽 7 条共 21 条，跑双版本+Judge 后生成 golden_verdicts 留空待人工填（scripts/blind_eval_run.py:36-121）；blind_eval_report.py 对比 judge vs golden 出分歧率，<30% 通过、≥30% 调 Judge prompt（scripts/blind_eval_report.py:18-86）。实测 21 条：robust 19%、readability 24% 通过，task 62% 分歧暴露 Judge 幻觉盲区（log/2026-07-27-phase3-blind-eval/README.md:62-66）。 三、反馈闭环：分歧样本与失败 case 自动沉淀——EvalResult.case_verdicts 落 JSONL（src/skillforge/evaluator/__init.py:119-150），元 Agent _collect_failures 拉 B_better 样本做根因分析（src/skillforge/evolver.py:231-252），DECLINED patch 归档 runs/failures/ 成为负样本记忆（evolver.py:468-470）。

    L39 如何构建 Agent 的效果评估体系（Evaluation Framework）？有哪些主流的 Benchmark 维度？是依赖人工标注、LLM-as-a-judge还是线上业务指标？

    一句话回答：本项目构建"八维评估器 + 分层评估集 + 棘轮回归门槛 + 盲评校准"四层体系：结构 4 维静态打分、效果 4 维 Judge 配对 + 客观指标，人工盲评只做低频校准。

    弃题说明：纯 HTTP 八股，与本项目无关——SkillForge 是本地 CLI 单进程系统，硬约束"无外部 DB 服务、无云依赖"（ARCHITECTURE.md:15-19），无任何 HTTP 服务实现，仓库无 503/504 对应代码或文档，无法给出项目内作答，弃。

    展开细节： 一、弃题理由：全仓无 Web 框架依赖（pyproject.toml 无 FastAPI/Flask/Django 等），无网关/反代/负载均衡配置，交互入口是 CLI 与元 Agent pipeline（src/skillforge/state_machine.py、src/skillforge/evolver.py），存储是本地 SQLite/Git/JSONL（src/skillforge/storage/），与 HTTP 状态语义零交集；既有二_5-9_作答.md 弃题说明已记录同一结论，此处补锚点段使 match.json 每个候选 id 都有落点。

    二、一般性回答方向（若面试被问到）：503 Service Unavailable=服务器当前无法处理请求（过载/熔断/维护中），是"暂时性"状态、客户端可稍后重试、响应可带 Retry-After 头；504 Gateway Timeout=网关/代理在限定时间内未等到上游响应（上游慢或已死），责任方在链路中间层；502=上游连不上/返回非法响应。三者同属 5xx 但责任方不同：503 是本服务自己，502/504 是上游链路。排查：503 查负载/熔断/维护窗口与限流配置，504 查上游超时配置与慢查询。可类比本项目的"无 HTTP 但有超时/降级语义"：LLM 调用失败返回 None 等价拒绝、不阻塞主链路（src/skillforge/router/llm.py:76-80），Watchdog 24h 把孤儿 PREPARING 标 ABANDONED（src/skillforge/state_machine.py:142-159）——"上游不可用时快速失败并留下可审计状态"是 5xx 语义在非 Web 系统的对应物，可作为类比话术。
