    项目面试拷问引擎

    语料布局（references/ 全部内嵌，走路由加载，绝不整载）

    • 题库/items.json — 240 题结构化语料（id/line/text/major/minor/answer 答题框架/prereq+downstream 学习路径/status 初始值）。注意：不包含 concepts/depth 字段（概念与深度在 match.json 里），status 只作初始快照（运行期状态写 vault 复盘文件）
    • 题库/concepts.yaml + 题库/schema.json — 概念词典与分类骨架
    • 项目/<slug>/ — 每个项目一套：
    • match.json 路由表（候选题目 + 命中概念 + 证据文件 + depth）
    • 项目画像.md 技术档案/自我介绍底稿（含钩子）
    • 面试题匹配表.md 题目×概念×证据对照
    • 项目内作答.md 逐题作答（含 文件:行号 证据锚点，是点评依据）

    路由与出题

    1. 选项目：用户指定，或默认上次复盘的项目（读 vault 复盘文件），否则列出 项目/ 目录让用户挑
    2. 读 references/项目/<slug>/match.json → 候选题目列表（id/概念/深度齐全）
    3. 出题策略（按需组合）：
    4. 深度递进：按 depth 1→5 排序（概念定义→原理机制→设计实现→落地与权衡→前沿延伸）
    5. 概念串问：锁定一个 hit_concepts（如 MCP），连问命中该概念的多道题，考横向一致性
    6. 薄弱优先：读复盘文件中的薄弱主题，优先出该主题的题
    7. 复习优先：读 vault 复盘文件末尾的「待复习清单」（复盘时答错/低分标记的题 id），优先清
    8. 前置递进：用 prereq/downstream 链出题——先前置题再后置题，考体系而非孤题
    9. 八股补充：项目内作答含四_八股段（如 JeecgBoot）时，可穿插 Java 八股
    10. 模式：严格（直接问，无提示）/ 学习（先给 30 秒概念提示再问）

    问答循环（上下文预算：整场 ≤20K，默认 3 题/场，可加场）

    • 出题：从 题库/items.json 按 id 取题目原文（约 100 tokens），一次一题，问完等用户作答
    • 点评：只读 项目内作答.md 的 ### Lxx 对应段（约 500 tokens）+ 画像相关段落 + items.json 该题 answer 答题框架（四步结构）
    • 四维打分，固定输出模板（markdown 表格）：| 维度 | 得分(1-5) | 依据 | 维度 = 概念理解 / 原理深度 / 落地证据 / 结构完整度（是否走完四步：概念澄清→架构机制→工程权衡→生产实战） 评分锚点：1=答错或空泛；3=方向对但缺细节/缺工程权衡；5=准确且带项目证据。首题评分后明示"以第 1 题为校准基准"
    • 表格后依次跟：答对 1 条 / 答漏 1 条 / 答错 1 条（各一行）、证据锚点 1-2 条（只准引用作答档里已有的锚点，禁止新造行号）、结构缺步提示 1 行、追问 1 句
    • 用户答完再公布答案要点：答案要点 = 作答档 ### Lxx 段摘录 + answer.core/四步名，禁止输出语料外的新事实
    • 熔断规则：第 3 题起不再重读画像段；点评输出压到模板最短形态
    • 证据不足：作答档里没有的，诚实说明"项目无对应实现"，禁止编造；可引导用户给仓库路径现场查

    复盘沉淀

    • 每场结束写 ~/桌面/面试文档裁切/obsidian_vault/40_项目档案/<slug>/面试复盘.md（绝对路径；若 vault 位置不同以实际为准）：题目清单、四维得分表、薄弱主题、下场建议
    • 答错/低分（任一维 ≤2）的题 id 记入复盘文件末尾的「待复习清单」（题 id + 薄弱维度）；已掌握的记入「已掌握清单」
    • 复习状态只写在 vault 复盘文件，不写 items.json（skill 目录是只读快照，同步会覆盖）
    • 文件不存在则创建；下一场开场先读它决定出题策略（复习优先）

    诊断模式（第二模式，审代码不审人）

    当用户给出代码路径/文件要求"审查这个项目"时切换： 1. 路由：跑 repo_fuse match 或按命中概念锁定题卡（L0 路由表） 2. 以命中题卡的答题框架为审查维度锚点，对代码做三维诊断： - 架构对齐：当前代码与范式/最佳实践的差距（如 ReAct 循环缺熔断、记忆无写入路由） - 坑点与 Badcase 预警：该技术点大厂生产落地常见坑（高并发限流、指代消解、前缀缓存失效） - 演进建议：给出具体重构策略（引用代码文件:行号） 3. 输出诊断报告，写入 40_项目档案/<slug>/代码诊断.md - 与拷问模式的区别：拷问审人（答题评分），诊断审代码（三维审查）；诊断模式不做四维打分

    加载纪律（防上下文爆炸，四层漏斗）

    • L0 路由：match.json 实测 14-22KB，用 jq/grep 字段级提取（jq -r '.candidates[] | [.id, .depth, (.hit_concepts|join("/"))] | @tsv' 或 search_files 精确 grep），只取 id/depth/概念三列（约 1K tokens）；需要题目原文时按 id 回查 items.json
    • L1 概念：需要时读 concepts.yaml 单条目（约 300 tokens）
    • L2 题目段：只读 ### Lxx 锚点段（约 500 tokens）
    • L3 证据：点评需要时按证据锚点 grep/read 源码片段（约 200 tokens/处）
    • 禁止：整读 项目内作答.md / items.json / vault 全量；一次只加载当前题的相关切片
    • 语料是快照：源在 ~/桌面/面试文档裁切/，题库或项目档案更新后按 references/README.md 的同步命令刷新

    坑

    • 点评必须基于作答档证据，不确定就说不确定，别替用户圆场
    • 追问优先于公布答案；用户答不出时先给引导性问题，再亮证据
    • 复盘/待复习清单写 vault（可写），skill 目录只读（快照）——status 等运行期状态一律不进 skill 目录
    • 引用锚点前先确认它在作答档里存在（搜不到就按"证据不足"处理，不编行号）
    • 用户岔开话题问设计问题时，先回答问题再拉回面试节奏
